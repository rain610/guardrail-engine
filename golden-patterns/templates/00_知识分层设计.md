# 知识分层设计 —— 谁装正文，谁装指针

> 面向：接入 harness 的同事、维护 harness 的人、以及要判断「这条规则该写在哪」的任何 agent。
> 一句话：**正文只有一份；客户仓只放指针 + 客户独有。**
> ⚠ 本文写的是**目标形态**。哪些已经到了、哪些还没，看 §四 各机制的状态、§五 的状态列、§七 的现状列。
> （§四 M2/M1/M3 已于 2026-09-19 落地；**33 个客户仓瘦身仍未做**，见 §六 风险。）

---

## 一、唯一判据

一条规则改了，**已经在用的人怎么收到这次改动？**

- **收得到** → 这一层可以装这条规则的正文
- **收不到** → 这一层最多放指针，**不放正文**

这条判据会否掉一个最常见、听起来也最合理的答案 ——「通用的规则统一放全局守则」。
理由见 §四 M1：全局守则**以前根本没有更新路径**（M1 已于 2026-09-19 补上）。

## 二、四层

按**「规则怎么进 AI 上下文」**分层。**不按「通用 / 专用」分层** —— 那条轴上「通用的放哪都行」，
答案不唯一；而传输机制这条轴上，每一层只有一个解。

| 层 | 住哪 | 怎么进上下文 | 更新路径 | 装什么 |
|---|---|---|---|---|
| **L0 规则本体** | `<HARNESS>/checks/` + `config/harness.yaml` | **git 钩子自动跑**，不需 AI 配合 | `git pull` | **能机械判定的一切** |
| **L1 入口路由** | `~/.eagle-agents/GLOBAL_AGENTS.md` | 各工具自动加载 | ✅ **哨兵分区重渲染**（M1，2026-09-19） | 只放「**怎么找**规则」 |
| **L2 知识库** | `<HARNESS>/golden-patterns/` | **按需读**（AI 主动） | `git pull` | 判不了的规则、范式、**端级摘要** |
| **L3 仓级** | `<客户仓>/AGENTS.md` + `CLAUDE.md` | 各工具自动加载 | 人工 | **客户独有 + 指针** |

**L2 同时装范式与端级摘要**（`templates/AGENTS_{pc,h5,backend}_slim.md`）—— 「端级」不是独立一层：
客户仓**不需要再存一份端级正文**，放指针指过来就行。少一层，就少一处副本。

### 为什么设计重心是「往 L0 推」

**L0 是四层里唯一不靠 AI 配合的层。** L1 / L2 / L3 全都要 AI 主动去读，读到与否取决于它当天的心情和
上下文长度；只有 L0 是 git 钩子跑，AI 想绕也绕不开。

这正是 harness 自己那条原则的展开：**硬约束在 git 钩子，软约束在 AGENTS.md**。
所以一旦一条规则**能被机械判定**，它就该离开 md、进 `checks/`。

> **实测**：`AGENTS_pc_slim.md` 的 7 条「核心规则速记」里，**3 条已经有活的规则体**
> （①→`PC-ELDENY`/`PC-COMP`、②→`PC-AXIOS`/`PC-ELMSG`、⑤→`PC-VAUTH`）；同页「检查项」那一行的
> 6 项也全在规则层（`PC-CONSOLE`/`PC-IP`/`PC-TODO`/`PC-COMP`/`PC-VFOR`/`PC-EOL` ——
> 实测这 9 个规则 ID 都存在于 `checks/pc_ruleset.py`）。**这些正文本来就不该写在 md 里** ——
> md 里那份是第三次抄写，且**没有任何机制保证它和 `checks/` 同步**。
> ⚠ 数的时候要分清「**铁律**」（7 条编号）与「**检查项**」（另一行）—— 别把两者加成一个数。

## 三、客户仓的最终形态

```markdown
# <客户> <端> 仓 —— AI 编码规则

## 端级规则
见 `<HARNESS>/golden-patterns/templates/AGENTS_h5_slim.md`（入口地图 + 端级事实；本端通用）

## 本仓独有（同事的机器上不会有的知识）
- 选人必须走 `windowChooseUser`，不要自己拼弹窗（gxgk）
- 构建：`npm run build:h5 -- --mode gxgk`

## 项目知识库
<VAULT>/concepts/customers/<客户>/
```

**只有「本仓独有」小节是真正的新增内容**，其余三节全是指针。
`CLAUDE.md` 仍是**一行** `@AGENTS.md`（Claude Code 不原生读 AGENTS.md，官方推荐桥接即首行 @import）。

> **`<VAULT>` 在哪儿被解释**：**不在客户仓里**，也不在引擎仓里 —— 它写在用户级守则
> （`~/.eagle-agents/GLOBAL_AGENTS.md`）的**哨兵区之外**，也就是每台机器自己那一份。
> 这是刻意的：客户仓的 `AGENTS.md` 随仓分发给所有人，里面**只该出现占位符**；
> 而「这台机器的知识库根在哪」是**本机事实**，写进随包分发的文件就会一并分发给每个同事。
> ⚠ 同事机器上没有这个目录 —— 用户级守则里那句就是写给他们看的：**忽略这一节即可**，
> 它不参与门禁、不影响改代码。所以别为了「把 `<VAULT>` 填上」去改客户仓的 `AGENTS.md`。

### 为什么必须这样：复制到 N 份的正文必然漂移

- **2026-09-19 审计**（判据 = 跨文件一字不差地重复）：33 个客户仓的 AGENTS.md 里，
  通用段 **85 行** + 半通用段 **147 行** = **232 行是副本**；真正独有 **551 行**。
  去重后「通用模板句」只有 **5 句**。
- **半通用段是更贵的问题**：H5 的「安卓 WebView 壳限制：常驻显式按钮，不依赖 popup/长按」重复在
  **8 个 H5 仓** —— 这是**端级**事实，本该写一次；而 gxgk 的 `windowChooseUser` 只出现在 **1 个仓**，
  那是真·客户独有，**必须留**。
- **实测 29 份**客户仓 AGENTS.md 含裸盘符路径
  （`cd <客户仓父目录> && grep -l '[A-Za-z]:[/\\]' $(find . -maxdepth 2 -name AGENTS.md)`；
  ⚠ 必须限定在仓根那一层 —— 用 `grep -r` 会顺带扫进深层 AGENTS.md，数会多出来）。
  其中**提到 harness 路径的 28 份，28 份写的都是本机盘符**，在本机之外**必然失效**；
  这条路径躺在 28 个仓里没人发现 —— 因为「28 个仓都有」本身让人以为它没问题。
- **⚠ 上面这条把「那一类路径」数漏了一个名字**（2026-09-22 补齐）：它只数了「harness 路径」，
  漏了**知识库根** —— 实测 **29 份**写的是维护机上的 `D:/KnowledgeVault/concepts/…`。
  「28/28 都是本机盘符」这个结论本身没错，错的是**它让人以为已经数完了**：于是修 harness
  那 28 处时，整整一类没被碰过 —— `target_form` 早先只把引擎仓路径换成 `<HARNESS>`，
  搬迁行里的知识库根一路照抄，**22 份产物全部**带着维护机的路径出货，直到 09-22 才由
  `portable()` + `VAULT_ROOTS` 治掉（锁：`tests/test_agents_scaffold.py` 里那组
  `TestVaultRootNeverShipsAsAMachinePath`，带注入证伪）。
  **教训：清点「某类东西还剩几份」之前，先数「这类东西有哪些名字」——
  少列一个名字，扫得再仔细，那一类也是零。**
- **活样本**：`README_推广接入.md` 自己写着「`AGENTS.md` — ✅ **6 仓**已有」，实测 **33 仓**。
  **连维护者手写的数都会漂**，这就是「正文不下发」最硬的论据。

## 四、三个必须补的机制

### M1 · 全局守则由「只创建一次」改为「哨兵分区重渲染」

**现状（已核实）**：`sandbox/bootstrap_agent_env.sh` 用 `if [ ! -f "$GLOBAL_SRC" ]` 守卫，
else 分支的注释明写「已存在时**不动它**（里面可能有你自己加的规矩）」；`upgrade.py` 也不碰它。
文件 `~/.eagle-agents/GLOBAL_AGENTS.md`（1448 字节）**不在任何 git 仓库内**（`git rev-parse` = fatal）。
→ **写进去的规则永远到不了已经有这个文件的同事那里。**

**改为哨兵分区**：

```markdown
<!-- HARNESS:BEGIN 本区由 harness 渲染，请勿手改 -->
…入口路由：受管仓清单怎么查 / 怎么跑门禁 / 被拦了怎么办…
<!-- HARNESS:END -->

（以下你自己加的规矩，harness 永不触碰）
```

`bootstrap_agent_env.sh` **每次运行只重写哨兵之间**，保留用户的追加段。既守住了原注释那份善意，
又补上了它缺的更新路径。渲染方式沿用工程里已有的 `sandbox/install_shim.py` 的
`render()` / `PLACEHOLDER` 范式（`__HARNESS__` 占位符 + 创建时 `sed` 烘入本机路径）—— 不发明新机制。

### M2 · 补 `AGENTS_h5_slim.md`，并把模板重新定位

- **缺口**：`templates/` 现在只有 PC + backend，**没有 H5**；而 H5 有 **10 个客户仓**、
  **24 份组件手册**（`golden-patterns/h5/组件手册/h5/eagle-*.md`）。H5 同学拿不到端级摘要。
- **定位要改**：模板是「**入口地图 + 端级事实摘要**」，**不是规则正文的副本**。
  7 条铁律里**带规则正文的那 3 条**（§二实测：① ② ⑤）**删掉正文**，换成**规则 ID 指针**：

  ```markdown
  2. 请求走 `@/utils/request` —— 门禁 `PC-AXIOS` 会拦；改法见 `pc_components_request.md` §三
  ```

  这样模板才**可以安全地下发到每个仓**（不再有第二份正文，也就没有漂移源）。

⚠ **不能直接把 PC 模板套到 H5**：PC 模板写「新增业务页面用 JS」「86 个全局组件」
「注册到 `registerGlobComp.ts`」—— 对 Vue 2.6（Options API）的 gxgk 是**反向误导**。

### M3 · 让「先读范式」不靠自觉 —— 用 `pre-edit` 钩子

**这是整套设计里最关键的一环**，因为 §二 说了 L2 全凭自觉。

`harness/hooks/pre-edit.py` **时机正好**（改码前），但原先只打印一句「确保方案已确认」。
现在它按 gate 名推出**该端的范式入口**并打印：

```
[pre-edit] 动手前先加载知识（pc 端）—— 按任务选，不要全读：
  · 端级规则地图：<HARNESS>/golden-patterns/templates/AGENTS_pc_slim.md
  · 端范式目录：<HARNESS>/golden-patterns/pc
  · 端到端范本：<HARNESS>/golden-patterns/endtoend
```

**⚠ 一处设计校正（2026-09-19 实现时发现）**：本文最初写的示例是「直接推出**该读哪一份**，
如 `pc_page_patterns.md`（新增页面）」。**那做不到**：`pre-edit.py <gate名>` 的签名里
**没有文件路径**，只有一个 gate 名 —— 由它最多能推出**端**（pc/h5/backend），
推不出任务类型（是新增列表页、还是改上传？同一端同一批文件都可能是）。
所以实际实现打印**端级三行**，把「哪份」交给端级模板里那张「按任务 → 必读」表 ——
agent 自己知道任务是哪一类，它缺的只是「入口在哪」。

两条落地约束（都已满足）：
- **端从 `checks/file_types.kind_of()` 推**，不另写映射 —— 那是全仓 gate名→端 的既有单一来源。
  认不出端的 gate 名走兜底分支，**不猜端**（猜错比不报更坏：让你读 H5 范式、门禁却按 PC 拦你）。
- **范式路径由 kind 推导**（`golden-patterns/<kind>/`、`templates/AGENTS_<kind>_slim.md`），
  不写死清单。清单就是副本，副本就会漂 —— 本次就当场撞见一例：`golden-patterns/index.md`
  的「按端速查」表漏登记了 6 份新风范（它们 2026-09-07 就建好，表 09-12 改过一轮仍没带上）。

配套锁：`tests/test_hooks_chain.py::test_pre_edit_prints_paradigm_pointer` —— 断言三个端的端级
模板都在磁盘上（**防「钩子还在、提示已静默失效」**，正是 M1 那个病的同一形态），
且 CLI 恒放行、认不出端时走兜底。

**还没做**：`post-edit.py` 的签名是 `<gate名> [文件...]`，**能拿到具体文件**，
原则上可以报得比端级更准（如「改的是 `.vue` 且在 `views/` 下 → 大概率新增页面」）。
留待后续，别为它发明规则匹配 —— 拿文件扩展名猜任务类型很容易猜错。

### 4.1 判据：按**行**判定，不按**端**判定（2026-09-19）

这一步原先被当成一道按端分类的判断题 ——「PC 端模板缺归宿所以先别动，后端/H5 全有归宿所以能删」。
**那个判断会过期**，而且过期时没有任何东西会响：PC 模板补上归宿的那天它不成立，后端/H5 冒出
一条无归宿新行的那天它也不成立。过期的判据没人知道该重跑什么。

现在的判据只有一句，且逐行问：

> 这一行，删了以后读者去哪儿找它？那个地方**当下**真的有这条东西吗？

- 求得到 + 锚点当下求证得到 → **可删**
- 求不到（或锚点指空）→ **不删**，原样留在「本仓独有」，并进「待迁清单」

于是「PC 现在不能删 / 后端现在全能删」不是两种模式，而是**同一张表在两个端的当前取值**。
往 `sandbox/sink_table.txt` 加一组 `[归宿]/[锚点]/[行]`，重跑，那一行自动从「待迁」挪进
「可删」—— 工具一行都不用改。**「待迁清单」反过来就是端级模板的待办**，
所以「瘦身」和「补模板」是一个环，不是两件事。

判据有两条**刻意选在安全侧**的取舍：

1. **归一化后精确相等，不是子串。** 比对前把引擎仓绝对路径（正/反斜杠两种写法）抹成 `<H>` 并
   折叠空白。不做归一化，这套判据**只在写表的人那台机器上成立**（同事 clone 到 `D:/dev/`，
   同一个仓的同一行会整片落进「待迁」）。差一个标点 → 落到「待迁」= **留而不删**。
2. **锚点要能求证到。** 改 `AGENTS_*_slim.md` 的措辞却忘了同步本表，工具会报「指针指空」，
   那几行自动退回待迁 —— 不误删，但**也不静默少删**（所以出声）。这与 `global_agents.stale_note`
   是同一手。

落地物：

| 物 | 是什么 |
|---|---|
| `sandbox/sink_table.txt` | 归宿表（手写，工具的**唯一**判据来源；**11 组 / 19 行** —— 2026-09-19 二次实测，首测 8 组 / 13 行，见下） |
| `sandbox/agents_audit.py` | 体检工具。**没有任何写入路径** —— 不开 write 模式、不建目录、不碰客户仓 |
| `tests/test_agents_audit.py` | 21 条锁：指空出声、差一标点落待迁、路径归一化换机器仍成立、保留行逐字留、跑一遍不动客户仓 |

用法：`python sandbox/agents_audit.py`（汇总 + 待迁清单）· `--diff <仓键>`（出拟改 diff，只打印）。

**首次体检（2026-09-19，可复跑）**：33 个受管仓 → 29 有 `AGENTS.md`、4 没有
（`hy_h5` 只有遗留 `CLAUDE.md`；`hy_pc`/`zhongxin_h5`/`zhongxin_pc` 两份都没有）；
可删 134 行 / 搬迁 22 行 / 结构 14 行 / **待迁 152 行**（其中 111 行只出现在一个客户仓里
= 真·本仓独有，本来就该留下）。

**第二次体检（同日更晚，同一命令）**：可删 **159** 行 / 搬迁 22 行 / 结构 14 行 /
**待迁 127** 行（其中 108 行只出现在一个客户仓里）。
差异全部来自同日把 PC 页面开发技能并进 `golden-patterns/pc/`，给几组 PC 行补上了归宿：
+3 组 / +6 条 `[行]` → **+25 行**从待迁挪进可删（一条 `[行]` 往往覆盖多个客户仓，
所以 6 条能放出 25 行；例：`先找标本页再动手` 一条就命中 7 个仓，见下）。

> ⚠ **两段数字都留着，这就是本文件要留的活证据**：中间没有改过任何一行工具的代码
> （`agents_audit.py` 一行未动），变的只是手写的归宿表。**手维的数会在同一天里漂两次** ——
> 所以别在别处引用这里的数字当"当前值"，要当前值就跑一遍命令。
> 同一处还有 `README_推广接入.md` 的「✅ 6 仓已有」：那句写于只有 6 个仓有 `AGENTS.md` 时，
> 而受管仓早已是 33 个、其中有 `AGENTS.md` 的是 **29** 个 —— 数一直没跟着动（2026-09-19
> 已改成「不写数、指向命令」的形态，§二 引过）。

## 六、风险（第 4 步之前必读）

1. **不能自动切分 33 个仓。** 「客户独有段」共 551 行必须逐字保住 —— gxgk 的 `windowChooseUser`、
   8 个 H5 仓的 WebView 壳约束，这类知识**删了不可恢复**。**逐仓出 diff 给人过目，不自动改。**
2. **哨兵渲染会覆盖哨兵内的手改。** 必须在文件里和文档里都写明「哨兵内勿手改」，否则有人改完
   下次被冲掉，会比现在更困惑。
3. **`hermes-agent` 不属于客户仓**（它有自己的 git 仓，AGENTS.md 29KB 是它自己的开发指南）。
   任何批量脚本都要显式排除。
4. 模板一旦下发就有了副本 —— **改模板前先确认它真的没有正文**（§二 的判据），
   否则等于亲手种下一份新的漂移源。
5. **判「门禁 ⟷ 文档冲突」前，先读规则的生效语义。** 门禁是**增量**的 ——
   `changed_lines` 非空时只拦新增行、存量行不拦提交（正文见 `README.md`「规则能力边界」末条），
   而客户仓文档常是在**描述存量现状**。把两者当成对撞，会让人去裁决一个不存在的矛盾。
