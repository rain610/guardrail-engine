# 黄金范本制造模板（Meta-模板 / 造范本的范本）

> **用途**：这是「如何造一份黄金范本」的标准工艺模板。你的业务域很多，无法一次做完——用这份模板，每个业务域按同一套结构、同一套提取流程、同一套验收标准产出，杜绝「凭印象编」。
> **配套**：`backend_api_authority.md`（后端接口权威索引，造任何后端业务范本先读它拿真实签名）。
> **位置**：本仓 `golden-patterns/templates/00_黄金范本制造模板.md`；按本模板造出来的范本存 `golden-patterns/endtoend/`。

---

## 一、一份范本固定包含的 8 个章节

> 第 0 章是骨架；第 1-6 章是内容；第 8 章是验收。**第 0/1/6/8 必须完整**，第 2-5 如果有就写、没有明确标注「无」。（对应真实范例：`relatedparty_audit_endtoend.md`）

### 0. 业务全景 + 文件地图（必须有）
用表格列出这个业务在仓库里的全部相关文件，各管什么：
| 层次 | 文件（相对路径） | 职责 |
|---|---|---|
| 实体 Entity | .../Entities/... | 数据表模型 |
| 仓储 Repository | .../Business/... | 业务逻辑/状态机 |
| 控制器 Controller | .../ApiController/... | HTTP 接口面 |
| DTO/ApiEntity | ... | 接口出入参 |
| 常量/Const | ... | 状态码/模板Code |
| 前端调用面 | PC/H5 页面 | 页面调用哪些接口 |

### 1. 核心状态机（灵魂，必须有）
- 列出**所有状态码**及含义（如 `5待审/10正常/-5退回`，标注来自哪个 Const）
- 画状态迁移：`什么动作 → 什么状态 → 为什么`
- 每个迁移给一段**真实代码** + 中文注释解释「为什么这么迁移」
- ⚠️ 特别标注**易漏的联动**（相关方审核最容易漏「账号连带恢复」）

### 2. 全局配置 / 字典 / 唯一记录（有则写）
- 全局一份的配置怎么存（如 `State=0 && Status=10` 唯一有效记录写法）
- 字典批量拉取约定

### 3. 核心接口约定（必须有）
- 分页列表、详情、提交、历史各接口的真实签名 + 前端 URL
- 输出转换是否用 `CamelCasePropertyNameSet/ForPage`
- 返回外壳 `this.Success()` / 校验 `WarningException`

### 4. 权限 / 通知 / 安全（有则写）
- 谁能访问（审核人列表/IsAdmin 等）
- 门禁放在哪层（**放 Repository 而非 Controller**，避免绕过）
- 通知逻辑（打回通知谁、怎么定位管理员、定时提醒）

### 5. 跨客户差异点（同源多客户必写）
- 用 `git ls-files` 对比同源客户分支，确定「有没有」和「改了什么」
- 表格：哪些是**通用**、哪些是**某客户特有**（带 【定制-客户】标记）
- 移植提醒：通用模块与特有叠加层**分开搬运**

### 6. 照抄清单（必须有，这是范本最大的复用价值）
- 假设「新增一个类似业务」，按 0-6 步给出照抄顺序（定常量→实体/DTO→触发埋点→业务仓储→配置+控制器→消息模板+调度→验证）
- **最容易踩的坑清单**（从真实验收总结，每条带教训）

### 7.（可选）前端 / 跨端联调段
- 如果这个业务有特殊前端写法（常驻按钮/状态tag/弹窗），引用对应技术范式

### 8. 范本自检（制造者必填，防「凭印象」）
| 检查项 | 通过标准 | 状态 |
|---|---|---|
| 真实来源 | 每个代码片段标注来源文件路径 | |
| 不编造 | 所有签名/状态码从读源码得出，不是记忆 | |
| 状态机闭环 | 每个状态迁移都有代码+为什么 | |
| 差异实证 | 跨客户结论用 git 命令验证过，非猜测 | |
| 接口名准确 | 用 `backend_api_authority.md` 对照（GetApiPageData 非 GetPageData） | |

## 二、提取流程（造一份范本的步骤）

1. **定位**：找该业务在仓库内的文件（`find` / `grep`），画出文件地图（第 0 章）
2. **读灵魂**：读 Repository 里的状态机方法（Trigger/Audit/状态流转）+ Const，提炼第 1 章
3. **读接口**：读 Controller 全部动作，对照 `backend_api_authority.md` 拿真实签名，写第 3 章
4. **读权限/配置**：grep 权限判断/唯一配置写法，写第 2、4 章
5. **验差异**：`git ls-files` 对比同源客户分支，写第 5 章（用事实，别猜）
6. **收敛照抄**：从「怎么新增类似业务」视角反向组织，写第 6 章
7. **自检**：填第 8 章验收表，任何一处评不过就回去补
8. **入库**：存 `golden-patterns/endtoend/`，文件名 `{业务}_endtoend.md`，并在 `golden-patterns/index.md` 的「业务端到端范本」表登记 —— **有锁**：`tests/test_docs_consistency.py::TestGoldenPatternsIndexIsComplete` 双向校验「目录里有 ↔ 索引里提到」，漏登记、或点了一个不存在的路径，都会报红（早先写的「在 `golden-patterns` skill 表格登记」是**指空**：没有这个 skill、也没有那张表）

## 三、批量制造策略（业务多、一次做不完）

> 你的 24 个业务域不可能一次全覆盖。用这个优先级：

1. **按你实际改的频率排序**：先做改得最多的 2-3 个（相关方审核/监督检查/证书审核已定位）
2. **分批做**：一次派 1 个（或并行 2-3 个）子 agent，每个按本模板产出，我逐一验收（读文件核对真实来源）
3. **积水泵式**：不是做全才用——做完一个，AI 改该业务时就先用上，边做边受益
4. **轻量版**：低频/简单业务可只做第 0/1/3/6 章（文件地图+状态机+接口+照抄清单），4 章版就够
5. **新增业务自动沉淀**：以后每做完一个新的复杂改造（带新业务逻辑），顺手补一份范本，库自动长大

## 四、质量红线（验收刚性标准）

- ❌ **任何代码片段没有来源路径 = 不合格**（无法验证）
- ❌ **状态码/签名凭记忆写**（如把 GetApiPageData 写成 GetPageData）
- ❌ **跨客户结论是推测**（必须 git 实证）
- ✅ 合格 = 每个「为什么」都能在源文件里找到依据
