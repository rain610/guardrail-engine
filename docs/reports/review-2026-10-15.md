## 一、总评

工程成熟度远超一般团队的自建门禁：增量语义（changed_lines 三态 + M12 传感器故障分档）、
提交期暂存内容 overlay（封死「暂存坏版本 + 工作区好版本」绕过）、注入通道防线（门禁输出不复述豁免语法、
不回显豁免理由）、覆盖度自评（回答「传感器不响 = 质量高还是检测失效」）、126 条变异护盾、
月度台账轮转与锚定——这些都对，且互相咬合。

**针对两个痛点做的优化方向正确、实现质量高**：范式规则化（PC-VALIDATE / PC-ELFORM / PC-MODAL）
判定口径严谨（模板区挖空保行号、排除同名前缀防误报、先实测存量再定级）；路径解析链
（env → `harness:` 键 → `~/.agentguard/harness.path` → 向上找）+ 指针注入 + check ⑦ 机器无关性，
在本机实测闭环。

但核心结论是：**门禁目前主要在拦「卫生」，不在拦「范式」。** 这是「AI 写出的代码不用封装组件」
体感的结构性原因，不能归咎于 agent 不听话一句话。

## 二、痛点一：范式为什么没被参照（三层根因）

### 根因 1：可判定面太小

- 范式库 30+ 份文档，规则化的只有 4 个点（PC-VALIDATE / PC-ELFORM / PC-MODAL / PC-COMP）；
- PC-COMP 实际只拦 deny/dead/平行版组件，**「必须用 eagle-*」这件事本身没有规则表达**；
- H5 端范式规则为 **0**（H5-COMP 为收敛类且定向口径从未响过）；
- 候选表 P5（confirm 二次确认）/ P6（loading）/ P7（前端全量分页）仍是软约束。

### 根因 2：事前加载纯靠自觉

golden-patterns 是「先读再写」的约定，agent 不读就没有任何东西强制它。skill 触发词能否命中、
`<HARNESS>` 能否解析、能否挑对 1-3 份文档——每一步都会漏。Hermes 恰好是**没有编辑器钩子**的
CLI agent：没有 pre-edit / post-edit 强制点，编辑期只剩 skill 约定，兜底只有 pre-commit。

### 根因 3：事后纠偏不闭环（本次评审最关键发现）

- 后端 entity 规则命中时带 `see="golden-patterns/backend/entity-layering.md …"`，
  **PC / H5 全部规则一个 `see` 都没有**；
- agent 被拦的那一刻是它最愿意听话的时刻，文案却只说「应走 eagle-form」，不给样板路径；
- 范式库写得再全，命中文案到范式文档之间这条走廊没接上。

## 三、痛点二：路径链优化评审——**通过**，附三个剩余风险

统一解析链、指针注入 + 每仓恰好一份自检、check ⑦ 挪到业务仓通用层（外部评审 CRITICAL #1 修法正确）。
本机实测闭环：gxgk_pc 的 AGENTS.md 已带指针块并指向端级模板；`~/.agentguard/harness.path` 内容正确；
「别猜路径，让用户重跑接入脚本」的 fail-closed 取向正确。

剩余风险（按影响排序）：

1. **环境变量双轨**：`find_root()` 同时收 `AGENTGUARD_DIR` / `HARNESS_DIR`；
   `global_agents.py` 的报错文案教前者，指针块与 SKILL.md 教后者。`HARNESS_DIR` 太通用、易被其他工具
   撞名。建议文档统一主推 `AGENTGUARD_DIR`（保留 `HARNESS_DIR` 做兼容别名）。
2. **harness.path 无新鲜度校验**：挪仓后它指向旧路径，`find_root` 会静默落到下一级（引擎侧无害），
   但 agent 手动解析时会拿到死路径。建议 doctor 加一条显式项：
   「`harness.path` 指向的目录下必须存在 `harness/run_gate.py`」。
3. **台账 entry 空缺**：10 月台账 78/795 条无 `entry` 字段（含真实拦截 rc=1），
   「谁触发的」溯源断了。建议 run_gate 兜底写 `entry="run_gate"` 而不是留空。

## 四、建议清单（按杠杆排序）

1. **把范式指针补进 PC/H5 的命中文案（最便宜、杠杆最大）**
   给 `checks/pc_ruleset.py` / `checks/h5_ruleset.py` 各规则的 Finding 补 `see` 字段，
   对齐 backend R12 既有做法。例：PC-ELFORM → 「样板：`golden-patterns/pc/pc_vue_form_drawer.md` §一」。
   边界说明：09-30 决定「门禁输出不复述豁免语法」防的是门禁口吻被仓库内注释伪造；
   只读的文档路径不属敏感内容，后端已有先例，注入防线不破。

2. **继续范式规则化，下一批优先级**
   - **P7（前端全量拉取后 slice/filter 分页）**：机械可判，直接违背「后端分页」核心范式；
   - **el-dialog / el-drawer 直用升 error**：PC-ELFORM 已证明按行过滤机制能让 el-table/el-form
     上 error 而不炸存量，同一类违规却保留 warn 一条路径（PC-ELDENY），属口径不一致；
     ⚠ **2026-10-15 订正：本行只保留 el-dialog（批次 2 已落地）。el-drawer 无 `eagle-drawer`
     封装组件、业务决定抽屉直接用，列入禁止清单会变成指向不存在封装件的假规则 —— 后半句作废，
     并已在候选表 P4 / pc_CODE_RULES.md / pc_vue_form_drawer.md 三处陈旧清单同步清理（见批次 2c）。**
   - **H5 端**按候选表纪律先复量存量再定，别照搬 PC 规则。

3. **补 Hermes 的编辑期闭环**
   - SOUL/profile 硬绑定（README 里目前是「可选」）建议落成必做；
   - 加机读自证入口（如 `cli.py log --last 1 --gate <gate>`），让 agent 完成任务前能自查
     「这个仓过没过门禁」。台账数据齐全，缺的只是查询约定。

4. **覆盖度指标的盲区**
   PC-SYNTAX / H5-SYNTAX 显示「从未触发」，很可能是「没违规就不计数」而不是「没跑」。
   建议每规则增加 `checked` 事件计数，覆盖度才能区分「活跃且干净」与「根本没跑」。

5. **PC-VALIDATE 盲区自查**
   await 式 `await formRef.value.validate()` 在 eagle-form 封装下同样静默失败
   （封装层只在校验通过时零参调 callback），当前判据只抓 `(valid` 回调签名。
   按候选表纪律复量一次存量后再决定是否补规则。

6. **文档口径收敛**
   `harness-ok` 豁免语法的唯一出处是 harness 根 `AGENTS.md`，但 SKILL.md、
   `integrations/agent-rule-snippet.md`、`AGENTS_pc_slim.md` 仍各有一份完整语法。它们是静态分发件、
   不算破注入防线，但四份拷贝就是四个漂移点——建议都改成一句指路。

7. **小项**
   - 「共 12 家」客户数可从 gate 名前缀机器推导加锁（AGENTS.md 自己已标注会静默过期）；
   - `docs/reports/coverage-*.md` 建议随发版固定重跑，避免「哪些规则从没响过」年久失修。

## 五、结论

骨架是对的、执行是认真的，两个针对性优化（路径链、范式规则化）均予认可。核心矛盾是
**范式层与门禁层之间那条走廊没打通**：知识库全、可判定面小、命中后无指路、Hermes 类 CLI agent
无编辑期强制。完成建议 1、2、3 后，「用起来」的体感会有实质变化。
